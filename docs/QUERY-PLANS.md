# Планы запросов

Замер от 2026-08-27. До него в бэклоге стояло «не измерено»: индексы заведены
на всех таблицах с клиентом, а пользуется ли ими планировщик на объёме — никто
не смотрел, потому что базы с объёмом нет. У пилота порядка 1 200 заявок, а до
нескольких тысяч строк postgres честно предпочитает последовательный проход.
На такой базе «индекс не используется» не значит ничего.

Поэтому мерялось на синтетике. Что из этого следует и чего не следует —
в конце, в разделе «Чего замер не показывает».

---

## Что спрашивали у планировщика

Не «быстро ли у пилота» — у пилота быстро всё. Продукт многоарендный, и
вопрос был другой: **не читает ли кабинет одного клиента строки остальных.**
Это единственный вопрос, на который нельзя ответить чтением кода: условие
изоляции в запросе может стоять, а планировщик всё равно прочитает таблицу
целиком и отфильтрует потом.

Второй вопрос — где на самом деле уходит время дашборда. Ответ оказался
неожиданным и занимает половину этого файла.

## Стенд

```
postgres 16.14, отдельный контейнер, не рабочая база
51 клиент         · у измеряемого 40 000 заявок, у прочих по 12 000
640 000           заявок          (raw_mefi_leads, 218 МБ)
1 920 000         переходов       (mefi_lead_history, 375 МБ)
1 100 000         строк сводных   (daily / salesperson / source _kpi)
окно запроса      90 дней
```

Перекос намеренный: два продавца из восьми держат половину заявок, треть
заявок приходится на последние полгода, шестая часть — брак. На равномерном
шуме планировщик видит статистику, которой не бывает, и выбирает по ней.

Воспроизводится: `backend/scripts/load-fixture.sql` заполняет,
`backend/scripts/query-plans.py` гоняет настоящий код сервиса, планы снимает
`auto_explain` на стороне базы. Порядок команд — в заголовках обоих файлов.
Запросы не переписаны от руки намеренно: переписанный запрос проверяет
переписывание, а не продукт, а расходятся они как раз там, где интересно.

---

## Что намерялось

Прогретый кеш, второй прогон подряд.

| запрос | мс | план |
|---|---:|---|
| свод воронки (`daily_kpi`) | 0.26 | Index Scan `ix_daily_kpi_tenant_date` |
| ставки последнего дня | 0.02 | Index Scan + Limit |
| разрез по источникам | 2.92 | Bitmap `ix_source_daily_kpi_tenant_date` |
| выручка по дням | 0.20 | Index Scan + Sort |
| **застрявшие оферты** | **112.10** | вид + двойной проход по истории |
| ведомость продавцов | 0.70 | Bitmap `ix_salesperson_daily_kpi_tenant_date` |
| маркетинг: ряд по источникам | 0.95 | Bitmap `ix_source_daily_kpi_tenant_date` |
| маркетинг: сайт | 0.05 | Bitmap `uq_source_daily_kpi_tenant_source_date` |
| маркетинг: брак по источникам | 2.77 | Bitmap `ix_raw_mefi_leads_tenant_id` |
| маркетинг: всего по источникам | 3.01 | Bitmap `ix_raw_mefi_leads_tenant_id` |

**Экран продаж — 115 мс в базе, из них 112 приходятся на один запрос.**
Девяносто семь процентов. Остальные четыре запроса вместе занимают 3.4 мс.

## Изоляция на объёме: проверено, чисто

Вид `v_mefi_leads_active` выглядит опасно. Внутри него подзапрос по всей
истории **без единого условия**:

```sql
LEFT JOIN (
    SELECT tenant_id, lead_external_id, bool_or(...) …
    FROM mefi_lead_history
    GROUP BY tenant_id, lead_external_id      -- ни WHERE, ни клиента
) h_agg ON h_agg.tenant_id = r.tenant_id AND …
```

Читая это, ждёшь, что каждое открытие дашборда сворачивает 1.9 млн строк всех
клиентов сразу. **Не сворачивает.** Планировщик проталкивает условие
`tenant_id = $1` внутрь группировки — ему это разрешено, потому что
`tenant_id` входит в `GROUP BY`:

```
->  HashAggregate  (rows=40000)
      Group Key: mefi_lead_history.lead_external_id
      ->  Bitmap Heap Scan on mefi_lead_history  (rows=120000)
            ->  Bitmap Index Scan on ix_mefi_lead_history_tenant_lead
                  Index Cond: (tenant_id = '…'::uuid)
```

120 000 строк — ровно столько их у этого клиента, а не 1 920 000. Записано
здесь, чтобы никто не расследовал это заново: код выглядит страшно, план
в порядке.

То же верно для всех сводных таблиц — каждая идёт по своему составному
индексу `(tenant_id, date)`, а не по таблице.

## Где на самом деле уходит время

Запрос застрявших оферт читает `mefi_lead_history` **дважды**: один раз внутри
вида, второй — внешним `LEFT JOIN` за `MAX(changed_at)`. Оба прохода берут
одни и те же 120 000 строк и по 2 410 страниц каждый — из 5 794 страниц всего
запроса это 83 %.

Переписанный вариант считает и то и другое одним проходом, без вида и без
приведений типа:

```sql
WITH h AS (
    SELECT lead_external_id,
           max(changed_at) AS last_changed,
           bool_or(to_status_id = ANY (ARRAY[3,1])) AS reached_offer
    FROM mefi_lead_history WHERE tenant_id = :tid
    GROUP BY lead_external_id
)
SELECT … FROM raw_mefi_leads r LEFT JOIN h ON … LEFT JOIN mefi_salespeople ms ON …
```

Замер, по три прогона каждого:

| | мс | страниц |
|---|---:|---:|
| как было, через вид | 90 – 114 | 5 794 |
| одним проходом | 45 – 48 | 3 400 |

**Вдвое.** Наборы строк совпадают: 32 179 строк с обеих сторон, `EXCEPT ALL`
в обе стороны даёт ноль. Не «выглядит эквивалентно» — проверено.

### Как это сделано (2026-08-27)

Свернуть историю прямо в сервисе, отдельным CTE, было бы дешевле — без
миграции. Но тогда пришлось бы вынести туда `IN (3, 1)`: определение
«дошёл до оферты» живёт в этом виде и только в нём, а воронка у клиента
настраиваемая (`tenants.funnel_config`). Второе место для той же константы
дороже одной миграции.

Поэтому `MAX(changed_at)` считается там же, где уже считаются `BOOL_OR`, —
свёртка истории и так идёт, лишняя агрегатная функция в ней бесплатна, — и
приезжает столбцом `last_history_change_at` (миграция 012). Запрос в сервисе
после этого не нуждается ни во втором соединении с историей, ни во внешней
группировке, ни в приведениях к тексту.

Замерено на том же стенде, после миграции:

| | мс | страниц |
|---|---:|---:|
| было, внутри экрана продаж | 112 | 5 794 |
| стало, внутри экрана продаж | 68 – 80 | 3 399 |
| было, отдельным запросом | 88 – 101 | 5 794 |
| стало, отдельным запросом | 49.5 – 51.3 | 3 399 |

Эквивалентность переспрошена уже на новом виде: 32 179 строк с обеих сторон,
`EXCEPT ALL` в обе стороны ноль.

В плане история читается одним `HashAggregate` (2 410 страниц), внешней
группировки нет, а соединение с продавцами планировщик берёт вложенным циклом
с `Memoize` по `assigned_to_id` — то самое, чего не позволяли приведения.

Заодно ушла тавтология: `AND v.lifecycle NOT IN ('junk')` во внешнем запросе
ничего не значило, потому что вид и так отдаёт только `'active'` и `'lost'`.
Держалась она на том, что её никто не проверял.

Поведение запроса теперь закреплено: `tests/integration/test_stuck_offers.py`,
по заявке на ветку — оферта по статусу, по флагу, только по истории, без
истории вовсе, проигранная, свежая, недошедшая, брак, чужой клиент. Тест
написан против СТАРОГО запроса и увиден на нём зелёным, семь мутаций убиты
на обоих. Прежний тест мокал `session.execute` и о самом SQL не знал ничего.

Заодно уходят три вещи помельче:

- **`GROUP BY` во внешнем запросе.** Он сворачивал 102 000 строк, чтобы взять
  `MAX` — а `MAX` уже посчитан в CTE.
- **Приведения `ms.external_id::text = v.assigned_to_id::text`.** Из-за них
  индекс `ix_mefi_salespeople_tenant_external` для этого соединения непригоден
  в принципе. Сегодня это ничего не стоит — продавцов восемь, планировщик
  берёт хеш, — но индекс там мёртвый груз, а не защита.
- **Оценка строк вчетверо ниже правды** (7 752 против 32 179, 23 025 против
  102 000). Пока безобидно: хеш-соединения выбраны верные. Но четырёхкратный
  недооценок — ровно то, от чего планировщик срывается в nested loop.

## Индекс, которого нет

Оба маркетинговых запроса фильтруют `raw_mefi_leads` по клиенту **и по дате
создания**, а индекс есть только по клиенту. Планировщик берёт все 40 000
заявок клиента и выбрасывает 31 704 из них уже после чтения:

```
Bitmap Heap Scan on raw_mefi_leads  (rows=8296)
  Rows Removed by Filter: 31704
  ->  Bitmap Index Scan on ix_raw_mefi_leads_tenant_id  (rows=40000)
```

С индексом `(tenant_id, created_at_source)`, по шесть замеров:

| | мс |
|---|---|
| без индекса | 2.72 · 2.77 · 2.84 · 2.94 · 3.01 · 3.08 |
| с индексом | 1.27 · 1.32 · 1.32 · 1.36 · 1.38 · 1.43 |

Индекс весит 6.6 МБ на 640 000 строк — около 0.4 МБ на клиента.

Выигрыш в полторы миллисекунды сам по себе не повод заводить индекс: у записи
тоже есть цена. Важнее форма. Без индекса работа пропорциональна **всем**
заявкам клиента за всё время, с индексом — только окну. На пилоте с его
1 200 заявками разницы нет вовсе; на 400 000 это 29 мс против 2.

## Мелочь, замеченная по дороге

`ORDER BY days_stuck DESC NULLS LAST LIMIT 50` не имел разрешителя ничьих:
при совпадающих сроках нельзя было сказать, какие именно пятьдесят оферт
увидит человек. Добавлено `, v.external_id` — одной строкой, в том же
проходе.

## Чего замер не показывает

- **Данные синтетические.** Он ловит «индекса нет вовсе» и «условие под
  функцией — индекс не берётся». Он не ловит перекос, которого я не угадал:
  реальные источники, статусы и продавцы распределены иначе, и на каком-то
  запросе планировщик может выбрать другое.
- **Кеш прогрет, диск не участвует.** Все страницы `shared hit`, ни одного
  `read`. На сервере с холодным кешем числа будут другими — но соотношения
  между запросами, а именно они здесь и интересны, сохранятся.
- **Один клиент, одно окно.** Мерялся самый крупный клиент и окно 90 дней —
  самая широкая кнопка в интерфейсе просит 366.
- **Ничего не изменено.** Это отчёт о замере. Переписывание запроса и индекс —
  отдельные решения, они записаны в бэклог с этими числами.
