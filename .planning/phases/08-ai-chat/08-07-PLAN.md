<objective>
Close CR-01 — the structural authorization bypass on every chat conversation endpoint. Today `ConversationRepository` filters only by `tenant_id`; the `ChatConversation.user_id` column exists but is never used as a query predicate. In a multi-user tenant any authenticated user can read, archive, or stream messages into ANY other user's conversation by guessing/replaying a UUID. CHAT-03 / SC#5 ("history stored per user") is structurally broken at the storage layer.

Per 08-VERIFICATION.md gap "SC#4 + SC#5":
- ConversationRepository accepts user_id and includes it in every WHERE clause (08-REVIEW.md CR-01 fix)
- send_message verifies conversation ownership BEFORE orchestrator.run_turn() — return 404 on mismatch
- Cross-user authorization integration test (User A POSTs to User B's conversation_id → 404)

Per 08-CONTEXT.md `<deferred>`: multi-user / per-user authorization beyond Phase 1's single owner user is NOT in this phase's scope. CR-01 is NOT that scope-creep — the `user_id` column already exists, the model docstring already says "owned by a single user inside a tenant", and CR-01 closes the gap of WIRING that existing column into the query predicate. No new user CRUD, no auth UI, no new schemas — just the missing predicate.

Purpose: Closes CHAT-03 (history persists per USER) and unblocks SC#5 by making CR-03 (Wave 2, plan 08-08) able to take user_id in its detached-session signature. CHAT-05 (number cross-check) is indirectly unblocked because cross-user reads currently surface wrong-user data through the orchestrator's history-load path.

Output: 2 source files changed + 1 unit test extension + 1 new integration test file. After this plan, plan 08-08 can pass user_id into schedule_title_generation, and the deferred-from-08-06 HUMAN-UAT can verify SC#5 conversation persistence per-user.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → FastAPI chat router | Authenticated user submits conversation_id in URL; today the server trusts that the conversation belongs to current_user.id without verifying — this is the boundary where CR-01 fires |
| chat router → ConversationRepository | The repository today trusts the caller to enforce per-user scoping; the caller (the router) didn't. CR-01 closes this by making per-user scoping structural inside the repository, removing the trust requirement from the boundary |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-08-01 | Information Disclosure (cross-user-within-tenant) | ConversationRepository.get_by_id / list_conversations / update_title / update_last_message_at / soft_archive | mitigate | Constructor now requires user_id; every SELECT and UPDATE filters by `(tenant_id, user_id)`. Defense-in-depth on top of the Phase 1 with_loader_criteria tenant-only seam. |
| T-08-01b | Information Disclosure (existence leak via 403-vs-404 distinction) | All chat conversation endpoints | mitigate | All cross-user accesses return 404 with the same Romanian copy ("Conversația nu există.") as a not-found legitimately-yours conversation. No 403 path. Attacker cannot distinguish "exists, owned by someone else" from "does not exist". |
| T-08-01c | Tampering (cross-user write via insert_conversation) | ConversationRepository.insert_conversation | mitigate | New ValueError raised when row.user_id != self._user_id, parallel to the existing tenant_id guard. Prevents a future contributor accidentally constructing the repo with current_user.id but writing a row with someone else's user_id. |
| T-08-03 | Information Disclosure (existence leak via timing on send_message) | send_message pre-flight ownership check | accept | The 404 is raised inside the same handler before the rate-limit + stream-lock are touched, so it returns synchronously. Timing differences between "fast 404" and "slow 200 stream" are inherent to the chat protocol and not mitigated here. |
</threat_model>
