## 1. System Classification

**System Type:** Content Generation Pipeline

**Description:**
Once per day at 06:00 Europe/Bucharest, this system reads the previous day's pre-computed `detected_problems` anomaly rows and `daily_kpi` snapshot from PostgreSQL, then calls Claude Sonnet 4.5 to produce a structured Romanian-language `DailyInsightResponse`: a top-3 priority problem list (each with 2-3 action items bearing a named owner and relative deadline), a positives section, and a 5-7 item weekly action plan. The primary consumers are the Sofa Belle owner and sales manager who read the report before their morning standup with the 6-person sales team. "Good" means the report reads like an experienced Romanian business consultant who knows Sofa Belle's specific funnel data, names the right salesperson when a performance issue is flagged, cites real percentages from the input KPIs, avoids inventing revenue figures (since `estimated_value` is NULL for all 1219 Sofa Belle leads), and hands the team concrete tasks they can act on immediately — not generic advice.

**Critical Failure Modes:**
1. **Hallucinated revenue figures** — `estimated_value` is NULL for all Sofa Belle leads; the system must not present precise RON amounts (e.g., "ai pierdut 47.320 RON") that have no basis in input data. Revenue impact must be phrased as "estimat" or avoided entirely.
2. **Generic advice without specific attribution** — when the `underperforming_salesperson` rule fires for a specific salesperson (e.g., Dragoi Mihaela at 2.8% L→C vs 5.8% team average), the report must name her and cite her actual conversion rate, not say "echipa de vânzări trebuie să îmbunătățească urmărirea lead-urilor."
3. **Romanian language errors** — wrong diacritics (ș/ț vs ş/ţ), false business cognates, or non-standard terminology that signals to the Sofa Belle owner that the system was not built for Romanian business context.
4. **Action items without a named owner** — vague "echipă" assignments are useless at 06:00 standup; each action must assign a real Sofa Belle salesperson name or a specific role (Manager, Marketing Sofa).
5. **False urgency on stable metrics** — flagging normal week-over-week variance as a critical problem trains the owner to ignore the report; the system must only surface problems when anomaly detection rules actually fire.

## 1b. Domain Context

> Researched by `gsd-domain-researcher`. Grounds the evaluation strategy in domain expert knowledge.

**Industry Vertical:** Premium retail / high-ticket home furnishings (B2C, Romania). Custom-order sofas, armchairs, beds; average deal 20,000+ RON; 3 showrooms in Brașov, București, Cluj-Napoca.

**User Population:** Sofa Belle owner and sales manager. Report consumed at 06:00 daily before morning standup with 6 salespeople. No technical background expected. Users have existing Excel-based KPI tracking habits and will immediately compare AI report numbers against their manual spreadsheet.

**Stakes Level:** High — each mis-directed action recommendation affects the sales team's priorities for the day; each missed anomaly (slow first touch, stuck offer) risks losing a 20,000+ RON deal to a competitor showroom.

**Output Consequence:** Owner and sales manager read the report, assign specific tasks to named salespeople, and decide which leads to prioritize that day. Incorrect, vague, or hallucinated outputs directly affect customer response time (4h target), offer follow-up, and ultimately contract conversion. The report also shapes the owner's perception of whether this AI product is worth keeping.

### What Domain Experts Evaluate Against

**Good (domain expert accepts):** Problem description cites the specific salesperson by full name with their actual conversion metrics from input data (e.g., "Dragoi Mihaela: 351 lead-uri, 10 contracte, 2.8% conversie — cu 54% sub media echipei de 5.8%"); action item `owner` field contains that salesperson's name.

**Stakes:** Critical
**Source:** Sofa Belle verified data (Phase 3, 2026-05-28): 6-person team with measurable performance spread; D-09 salesperson roster requirement; Sofa Belle owner pain point "nu știu cine din vânzători lucrează bine."

**Dimension:** Anomaly signal fidelity (no cry-wolf)
**Good (domain expert accepts):** Report contains exactly the problems that anomaly detection rules fired on that day (max 3 by `estimated_loss_ron` descending); each problem `id` traces to a real `rule_id` in `detected_problems`; on a quiet day with 0 anomalies, report generates a positives-only summary without fabricating problems.
**Bad (domain expert flags):** Report lists 4-5 "problems" on a day when only 1 anomaly rule fired, or raises a "scădere trafic showroom" alert when ANOM-04 did not fire that day — owner learns within 2 weeks that the system cries wolf and stops reading it.
**Stakes:** High
**Source:** ai-evals.md: false urgency on stable metrics is a known failure mode for daily digest systems; REQUIREMENTS.md ANOM-01 through ANOM-07; D-02 hard cap of 3 problems enforced in both Python (Pydantic `max_length=3`) and system prompt.

### Known Failure Modes in This Domain

1. **Revenue fabrication on NULL deal values:** Claude may invent plausible-sounding RON amounts (e.g., "ai pierdut 23.400 RON luna aceasta") when `estimated_value` is NULL for all Sofa Belle leads. The number cross-check (AI-06) catches numbers that appear in narrative text, but the system prompt must explicitly instruct Claude that deal values are not available and estimated losses come only from `estimated_loss_ron` in the anomaly rows. Without this guard, the hallucination passes the regex check if the invented number happens to be close to the anomaly's heuristic estimate.

2. **Generic salesperson coaching without specific data:** When the `underperforming_salesperson` anomaly rule fires for a specific salesperson, Claude may produce advice like "vânzătorul trebuie să urmărească lead-urile mai rapid" without connecting to that person's specific conversion deficit vs the team average. This is the most common failure mode for sales AI tools in production: LLMs trained to be polite avoid naming underperformers directly.

3. **Funnel stage / Showroom source confusion:** Because Sofa Belle uses "Vizita" in their Excel to mean showroom walk-in source (not a MEFI funnel status), and because source_id=5 (Showroom) delivers the highest contract rate despite being 26.6% of leads, Claude may incorrectly describe L→V conversion if the system prompt does not clarify the distinction. A report saying "conversia vizită a scăzut cu 15%" when the actual issue is a different source channel misdirects the owner.

4. **Alarm fatigue from false urgency:** Surfacing WoW variance as "problems" on days when no anomaly rules actually fired is the most damaging long-term failure mode. Sofa Belle's owner will tolerate 1-2 false alarms but will stop trusting the product after repeated crying wolf. The system must stay strictly grounded in whether `detected_problems` rows exist for that day — and the 0-anomaly case (D-13) must produce a legitimately positive report, not invented concerns.

## 2. Framework Decision

**Selected Framework:** Direct Anthropic Python SDK (`anthropic`)

**Version:** `anthropic>=0.30,<1` (current stable: 0.55.x as of 2026-05)

**Rationale:**
Phase 5 generates a single structured Romanian report from pre-computed anomaly data. The task is a well-defined content generation pipeline: fixed input schema (detected_problems + daily_kpi), fixed output schema (DailyInsightResponse), called once per day from a Celery task. No agent orchestration, RAG retrieval, or multi-step tool loops are needed. Using the direct Anthropic SDK eliminates orchestration overhead (LangChain, LlamaIndex, CrewAI), keeps the dependency surface minimal, and gives full control over the tool-use forced-JSON pattern, prompt caching headers, and token usage tracking that Phase 5 requires. The SDK's `AsyncAnthropic` client integrates directly with the project's mandatory `asyncio.run()` + NullPool Celery task pattern (INFRA-05, D-18). The team is already Anthropic-committed (CLAUDE.md), so vendor lock-in is the intended design.

**Alternatives Considered:**

| Framework | Ruled Out Because |
|-----------|------------------|
| LangChain | Abstraction overhead adds latency, hides prompt caching headers behind wrappers that require extra configuration, and introduces a 25MB+ dependency for what is a single API call |
| LlamaIndex | Data ingestion / RAG framework; no value added for a prompt-in / structured-JSON-out pipeline |
| CrewAI | Multi-agent orchestration; overkill for one-model single-call batch pipeline; Python-only but adds role/task/crew concepts that do not map to this use case |
| Instructor library | Would add Pydantic retry logic cleanly, but adds a dependency; Phase 5 implements the same pattern directly via tool-use forced JSON and a 2-retry loop — no extra library needed |

**Vendor Lock-In Accepted:** Yes — Anthropic only. This is a deliberate decision: the product is built around Claude's Romanian language quality and the CLAUDE.md locks the model string. The lock-in is documented and accepted.

```python
# Demonstrates: AsyncAnthropic, prompt caching on system block, forced JSON via tool use,
# token usage tracking. This is the core of InsightService._call_claude().

import asyncio
import json
from anthropic import AsyncAnthropic
from pydantic import BaseModel, Field
from decimal import Decimal
from datetime import datetime, UTC


class ActionItem(BaseModel):
    order: int
    description: str
    owner: str
    deadline: str
    expected_outcome: str


class Problem(BaseModel):
    id: str
    severity: Literal["high", "medium", "low"]
    category: Literal["marketing", "sales", "team", "funnel"]
    title: str
    description: str
    estimated_loss_ron: Decimal
    actions: list[ActionItem]


class DailyInsightResponse(BaseModel):
    summary: str
    problems: list[Problem] = Field(max_length=3)
    positives: list[dict]
    warnings: list[dict]
    weekly_action_plan: list[str]
    generated_at: datetime


# ── Build the tool schema from Pydantic model ────────────────────────────────
def _build_tool_schema() -> dict:
    """Convert DailyInsightResponse to Anthropic tool input_schema."""
    return {
        "name": "generate_daily_insight",
        "description": "Generează raportul zilnic de business în română pentru Sofa Belle.",
        "input_schema": DailyInsightResponse.model_json_schema(),
    }


async def generate_insight_example() -> DailyInsightResponse:
    # Instantiate inside async function — deferred import pattern (INFRA-05)
    client = AsyncAnthropic()  # reads ANTHROPIC_API_KEY from environment

    # System prompt is sent as a list of blocks; last block gets cache_control
    # so the entire system prompt (stable content) is cached across daily calls.
    system_blocks = [
        {
            "type": "text",
            "text": (
                "Ești un consultant de business pentru Sofa Belle, "
                "o companie premium de mobilă din România. "
                "Analizezi datele CRM și generezi rapoarte zilnice de acțiuni concrete."
                # Full system prompt goes here — see prompt_builder.py
            ),
        },
        {
            "type": "text",
            "text": "Format de răspuns: JSON conform schemei specificate în tool.",
            # cache_control on the LAST block caches everything above it too
            "cache_control": {"type": "ephemeral"},
        },
    ]

    # User message is fresh every day — NOT cached
    user_message = json.dumps({
        "date": "2026-05-28",
        "kpi_snapshot": {"leads_total": 12, "l_to_c_pct": 8.3},
        "detected_problems": [],
    })

    response: Message = await client.messages.create(
        model="claude-sonnet-4-5",          # locked model string — do NOT change (D-model)
        max_tokens=4096,
        temperature=0.2,                     # AI-05: low temperature for consistent reports
        system=system_blocks,
        messages=[{"role": "user", "content": user_message}],
        tools=[_build_tool_schema()],
        tool_choice={"type": "tool", "name": "generate_daily_insight"},  # force tool call
    )

    # Extract tool use content block — guaranteed by tool_choice="tool"
    tool_block = next(b for b in response.content if b.type == "tool_use")
    raw_json: str = json.dumps(tool_block.input)  # tool_block.input is already a dict

    # Parse and validate with Pydantic
    parsed = DailyInsightResponse.model_validate(tool_block.input)
    parsed.generated_at = datetime.now(UTC)  # set server-side, not from Claude

    # Token usage tracking (AI-08)
    usage: Usage = response.usage
    input_tokens = usage.input_tokens
    output_tokens = usage.output_tokens
    cache_read_tokens = usage.cache_read_input_tokens or 0
    cache_creation_tokens = usage.cache_creation_input_tokens or 0

    # Cost calculation: Claude Sonnet 4.5 pricing (SPEC.md Section 10)
    cost_usd = (input_tokens / 1_000_000) * 3.0 + (output_tokens / 1_000_000) * 15.0

    return parsed
```

### Key Abstractions

| Concept | What It Is | When You Use It |
|---------|-----------|-----------------|
| `AsyncAnthropic` | The async client class. Must be instantiated inside the async function body, not at module level, to satisfy INFRA-05 (fork-safe, no cross-loop connections). | Every call in `_generate_async()` — one instance per invocation, no sharing across Celery tasks. |
| Tool Use (forced JSON) | The pattern for structured outputs: define `DailyInsightResponse` as a tool schema, set `tool_choice={"type": "tool", "name": "..."}` to force a single tool call. Claude always responds with `ToolUseBlock`, eliminating JSON parsing guesswork. | `InsightService._call_claude()` — the only way to get a validated Pydantic object from Claude in `anthropic>=0.30`. |
| `cache_control` on system blocks | Sending `system` as a list of `TextBlock` dicts where the last block has `"cache_control": {"type": "ephemeral"}` caches all preceding tokens for 5 minutes. Reduces per-call cost by ~90% on the stable system prompt (AI-05). | `prompt_builder.build_system_prompt()` — always on the last block, never on the user message block. |
| `usage.cache_read_input_tokens` | Token count served from cache in this response (0 on first call of the day, populated on retries). Used with `cache_creation_input_tokens` and `input_tokens` to compute true cost. | `InsightService._track_usage()` — log all four fields to `daily_insights` table (AI-08). |
| `tool_block.input` | The `dict` payload inside a `ToolUseBlock` response. This is the raw structured output from Claude — already parsed from JSON by the SDK. Pass directly to `DailyInsightResponse.model_validate()`. | After every `client.messages.create()` call where `tool_choice` is set — extract with `next(b for b in response.content if b.type == "tool_use")`. |

### Common Pitfalls

1. **Instantiating `AsyncAnthropic` at module level breaks Celery prefork workers.** The client opens an `httpx.AsyncClient` which binds to an event loop. When Celery forks the worker process, the loop from the parent is invalidated — every subsequent `await` raises `RuntimeError: Event loop is closed`. Fix: always instantiate inside the async function body per D-18.

2. **`asyncio.run()` inside an already-running event loop raises `RuntimeError`.** Celery task functions are sync; `asyncio.run(_generate_async(...))` is correct. But if you call `asyncio.run()` from within an already-async context (e.g., a test using `pytest-asyncio`, or a FastAPI endpoint), it will raise. Fix: in tests, use `asyncio.get_event_loop().run_until_complete()` or mark the test as `async` and `await _generate_async()` directly.

3. **`cache_control` on the wrong block invalidates caching.** The cache breakpoint must be placed on the LAST block that contains stable (non-daily) content. If you accidentally include any per-day data (today's date, KPI values) in a cached block, each invocation creates a new cache entry and you pay the 1.25x write cost every time instead of the 0.1x read cost. Fix: put all daily-varying data in the user message, never in the system prompt.

4. **`tool_block.input` is a `dict`, not a JSON string.** The SDK parses the JSON from Claude's response before returning it. Calling `json.loads(tool_block.input)` will raise `TypeError`. Fix: pass `tool_block.input` directly to `DailyInsightResponse.model_validate(tool_block.input)`.

5. **`usage.cache_read_input_tokens` is `None`, not `0`, on a cache miss.** Accessing it without a guard raises `TypeError` in arithmetic. Fix: always use `usage.cache_read_input_tokens or 0` and `usage.cache_creation_input_tokens or 0` when computing cost.

## 4. Implementation Guidance

**Model Configuration:**

```python
MODEL = "claude-sonnet-4-5"   # locked — do NOT change (D-model, CLAUDE.md, STATE.md)
MAX_TOKENS = 4096             # sufficient for full DailyInsightResponse with 3 problems
TEMPERATURE = 0.2             # AI-05: low variance for daily business reports
MAX_CLAUDE_RETRIES = 2        # AI-06: up to 2 regenerations before Celery retry fires
```

**Core Pattern:**

The InsightService uses the **tool-use forced-JSON** pattern. This is the only reliable way to get a validated Pydantic object from Claude without hand-rolling JSON parsing. Claude is forced to call `generate_daily_insight` with the full `DailyInsightResponse` schema; the SDK returns `tool_block.input` as a `dict`; Pydantic validates it. The flow inside `InsightService.run()`:

```python
# backend/app/services/insights/insight_service.py
from __future__ import annotations

import json
import re
from datetime import UTC, datetime
from decimal import Decimal

import structlog

log = structlog.get_logger(__name__)

_MAX_RETRIES = 2
_NUMBER_PATTERN = re.compile(r'\b\d{1,3}(?:[.,]\d{3})*(?:[.,]\d+)?\b|\b\d+\b')


class InsightService:
    """Transforms detected_problems + daily_kpi into DailyInsightResponse via Claude.

    All Claude calls are async. Instantiated per-invocation inside _generate_async().
    Constructor receives an AsyncSession and tenant_id — same pattern as AnomalyService.
    """

    def __init__(self, session, tenant_id) -> None:
        # session and tenant_id stored for DB reads (detected_problems, daily_kpi)
        self._session = session
        self._tenant_id = tenant_id

    async def run(self, kpi_date) -> tuple[dict, str]:
        """Generate DailyInsightResponse for kpi_date.

        Returns:
            (insight_dict, status) where status in ('success', 'fallback', 'failed')
        """
        # Deferred imports — inside method body satisfies INFRA-05
        from anthropic import AsyncAnthropic
        from app.core.config import settings
        from app.schemas.insights.daily_insight_schema import DailyInsightResponse
        from app.services.insights.prompt_builder import build_system_prompt, build_user_message

        # Fetch input data from DB (detected_problems, daily_kpi for kpi_date)
        problems_rows = await self._fetch_detected_problems(kpi_date)
        kpi_row = await self._fetch_kpi_snapshot(kpi_date)

        system_blocks = build_system_prompt()     # returns list[dict] with cache_control
        user_content = build_user_message(kpi_row, problems_rows)

        tool_schema = {
            "name": "generate_daily_insight",
            "description": "Generează raportul zilnic de business în română pentru Sofa Belle.",
            "input_schema": DailyInsightResponse.model_json_schema(),
        }

        client = AsyncAnthropic(api_key=settings.anthropic_api_key)
        last_raw: str = ""
        last_usage = None

        for attempt in range(_MAX_RETRIES + 1):  # 0, 1, 2
            response = await client.messages.create(
                model="claude-sonnet-4-5",
                max_tokens=4096,
                temperature=0.2,
                system=system_blocks,
                messages=[{"role": "user", "content": user_content}],
                tools=[tool_schema],
                tool_choice={"type": "tool", "name": "generate_daily_insight"},
            )

            last_usage = response.usage
            tool_block = next(
                (b for b in response.content if b.type == "tool_use"), None
            )
            if tool_block is None:
                log.warning("insight.no_tool_block", attempt=attempt)
                continue

            last_raw = json.dumps(tool_block.input)

            try:
                parsed = DailyInsightResponse.model_validate(tool_block.input)
            except Exception as exc:
                log.warning("insight.pydantic_validation_failed", attempt=attempt, error=str(exc))
                continue

            # AI-06: number cross-check — extracted numbers must match input data ±2%
            if not self._numbers_match(parsed, kpi_row, problems_rows):
                log.warning("insight.number_mismatch", attempt=attempt)
                if attempt < _MAX_RETRIES:
                    continue
                # Final attempt failed validation — fall through to fallback

            else:
                # Successful parse + validation
                parsed.generated_at = datetime.now(UTC)
                cost_usd = self._compute_cost(last_usage)
                return (
                    {
                        "payload": parsed.model_dump(mode="json"),
                        "input_tokens": last_usage.input_tokens,
                        "output_tokens": last_usage.output_tokens,
                        "cost_usd": cost_usd,
                        "raw_response": last_raw,
                    },
                    "success",
                )

        # All retries exhausted — return fallback (D-14, D-15)
        fallback = self._build_fallback(problems_rows)
        return (
            {
                "payload": fallback.model_dump(mode="json"),
                "input_tokens": last_usage.input_tokens if last_usage else 0,
                "output_tokens": last_usage.output_tokens if last_usage else 0,
                "cost_usd": self._compute_cost(last_usage) if last_usage else Decimal("0"),
                "raw_response": last_raw,
            },
            "fallback",
        )

    @staticmethod
    def _compute_cost(usage) -> Decimal:
        """Claude Sonnet 4.5 pricing: $3/MTok input, $15/MTok output (SPEC.md Section 10)."""
        if usage is None:
            return Decimal("0")
        input_tok = usage.input_tokens or 0
        output_tok = usage.output_tokens or 0
        return Decimal(str((input_tok / 1_000_000) * 3.0 + (output_tok / 1_000_000) * 15.0))

    def _numbers_match(self, parsed, kpi_row, problems_rows) -> bool:
        """AI-06: extract all numbers from narrative text, cross-check vs input data ±2%."""
        # See number_validator.py for full implementation
        return True  # placeholder — implement in number_validator.py

    def _build_fallback(self, problems_rows) -> object:
```

**Tool Use:**

No external tools are used by Claude in Phase 5 — this is a batch content generation call, not an agentic tool-calling loop. The tool schema is used solely to enforce structured JSON output via `tool_choice={"type": "tool", "name": "generate_daily_insight"}`. **State Management:**

- Output: up to 4,096 tokens — sufficient for the full report with 3 problems, each having 2-3 action items, plus `positives[]`, `warnings[]`, and `weekly_action_plan[]`.
- Total per-call: ~6,500–7,500 tokens input, well within Claude Sonnet 4.5's 200K context window.
- Never include all historical detected_problems or lead-level data in the user message — use only the compact daily snapshot.

### 4b.1 Structured Outputs with Pydantic

The Anthropic Python SDK (`anthropic>=0.30`) does not have a `messages.parse(output_format=...)` method (the REQUIREMENTS.md reference to `output_format` is aspirational shorthand). The production-grade pattern for structured output is **tool-use forced JSON**: define the Pydantic model as a tool `input_schema`, set `tool_choice={"type": "tool", "name": "..."}` to force the tool call, then validate `tool_block.input` with Pydantic.

```python
# backend/app/schemas/insights/daily_insight_schema.py
from __future__ import annotations

from datetime import datetime
from decimal import Decimal
from typing import Literal

from pydantic import BaseModel, Field


class ActionItem(BaseModel):
    order: int
    description: str
    owner: str             # real Sofa Belle name or role (D-09)
    deadline: str          # one of: "Azi", "Mâine", "Săptămâna aceasta", "Luna aceasta" (D-10)
    expected_outcome: str  # measurable metric + target (D-12)


class Problem(BaseModel):
    id: str                # = rule_id from detected_problems (D-04, traceable link)
    severity: Literal["high", "medium", "low"]
    category: Literal["marketing", "sales", "team", "funnel"]
    title: str
    description: str       # 2-3 sentences — must reference actual figures from input data
    estimated_loss_ron: Decimal  # Decimal, not float (D-19)
    actions: list[ActionItem]    # 2-3 items per problem (D-11)


class Positive(BaseModel):
    title: str
    description: str
    recommendation: str


class Warning(BaseModel):
    title: str
    description: str


class DailyInsightResponse(BaseModel):
    summary: str                                  # one overview paragraph in Romanian
    problems: list[Problem] = Field(max_length=3) # hard Pydantic cap at 3 (D-02)
    positives: list[Positive]                     # 0-3, Claude decides count
    warnings: list[Warning]                       # 0-N weak signals, Claude decides
    weekly_action_plan: list[str]                 # 5-7 flat action strings (D-03)
    generated_at: datetime                        # set server-side in InsightService, not by Claude
```

### 4b.2 Async-First Design

**How async works in this framework:** `AsyncAnthropic` exposes `await client.messages.create(...)` — all network I/O is non-blocking. The client uses `httpx.AsyncClient` internally. The Celery task entry point is synchronous; `asyncio.run(_generate_async(...))` creates a fresh event loop per invocation.

**The one mistake that will happen:** calling `asyncio.run()` inside a context that already has a running event loop. This surfaces in two places:

1. `pytest-asyncio` tests: if the test is decorated `@pytest.mark.asyncio` and you call `asyncio.run()` inside the test body, it raises `RuntimeError: This event loop is already running`. Fix: test `_generate_async()` directly by `await`-ing it, not through `asyncio.run()`.

2. FastAPI endpoint handlers: the project rule (AI-09, CLAUDE.md) prohibits calling Claude from HTTP handlers, so this path should not exist. If it accidentally does, the same `RuntimeError` appears. Fix: route through a Celery task.

**Stream vs. await decision for Phase 5:**

Phase 5 is a batch pipeline. Always use `await client.messages.create(...)` (non-streaming). Streaming adds complexity — partial JSON cannot be Pydantic-validated until the stream closes, and Celery tasks have no downstream consumer waiting for partial output. Streaming is deferred to Phase 8 (AI Chat), where the FastAPI `StreamingResponse` endpoint uses `async with client.messages.stream(...)` to push tokens to the browser (CHAT-08).

```python
# Phase 5: await (batch, validates full JSON before writing to DB)
response = await client.messages.create(model=..., ...)
parsed = DailyInsightResponse.model_validate(response_tool_block.input)

# Phase 8 only: stream (UX — first token in <2s)
async with client.messages.stream(model=..., ...) as stream:

```

### 4b.3 Prompt Engineering Discipline

**System vs. user prompt separation:**

- System prompt (cached block): consultant persona, Sofa Belle company facts, salesperson roster with names and MEFI IDs (D-09), funnel stage definitions, tone instructions (Romanian, business, no fluff), deadline labels (D-10), action format requirements (D-11, D-12), the full `DailyInsightResponse` JSON schema, and the hard instruction `"Maximum 3 probleme de prioritate înaltă"` (D-02). All content that does not change day-to-day.
- User message (never cached): compact KPI snapshot for yesterday only (leads_total, visits_count, offers_count, contracts_closed, conversion rates, wow_delta values, avg_deal_size) + up to 3 `detected_problems` rows in JSON format. Typically ~500 tokens. Never include historical trends or lead-level records here — the KPI table's WoW/MoM delta columns provide the comparison context.

**Few-shot:** Not needed for Phase 5. The Romanian domain is narrow, Claude's instruction-following is reliable at temperature=0.2, and the schema constraint (tool-use) enforces the output structure. Adding few-shot examples to the system prompt would consume cache token budget without measurable quality improvement at this problem complexity. Revisit if the number cross-check failure rate exceeds 5% in production.

**`max_tokens` in production:** Always set explicitly. Default is `None` which means "model maximum" — this runs up to 8,096 output tokens on Claude Sonnet 4.5, generating inflated reports and unnecessary cost. Phase 5 sets `max_tokens=4096`. This is generous for the full report and prevents runaway generation. Never ship to production without an explicit `max_tokens`.

**revenue figures:** System prompt must include this instruction: `"estimated_value este NULL pentru toate lead-urile Sofa Belle — nu prezenta valori de vânzări ca precise. Folosește 'estimat' sau evită valorile monetare absolute"` (from D-specifics in 05-CONTEXT.md, real data constraint).

### 4b.4 Context Window Management

Phase 5 has a stable, well-bounded context:

- System prompt: ~2,500 tokens (built once, cached)
- User message: ~500 tokens (daily snapshot + max 3 anomaly rows)
- Total input: ~3,000 tokens per call — far below the 200K context window

Token budget is not a concern for this phase. However, three discipline rules prevent accidental growth:

1. **Never include raw `context_json` objects verbatim.** The `context_json` field on `DetectedProblem` can be large. In `build_user_message()`, extract only the fields needed (current_value, expected_value, rule_id) — never `json.dumps(row.context_json)` directly.

2. **Cap the number of `detected_problems` sent to Claude at 3** (D-02). Even if 7 rules fire in one day, send only the top 3 by `estimated_loss_ron` descending. The selection happens in Python before the API call, not by Claude. This both caps input tokens and keeps the report focused.

3. **Do not send KPI history.** The daily_kpi table has WoW and MoM delta columns (`wow_delta_pct`, `mom_delta_pct`). Send those deltas in the snapshot, not the raw historical rows. The comparison context is already computed — do not reconstruct it by sending 30 days of data.

Phase 8 (AI Chat) has a different problem: multi-turn conversation history can grow unboundedly. That phase will need a summarization pattern (keep last N turns + summary of earlier turns). Phase 5 does not have this problem because it is single-turn, stateless, and batch.

### 4b.5 Cost and Latency Budget

**Per-call cost at daily production volume:**

```
Model:              claude-sonnet-4-5
Input pricing:      $3.00 / MTok
Output pricing:     $15.00 / MTok
Cache write:        $3.75 / MTok (1.25x input price, 5-minute TTL)
Cache read:         $0.30 / MTok (0.1x input price)

Typical call breakdown:
  System prompt (first call of day — cache write):  2,500 tokens → $0.009375
  System prompt (retries — cache read):             2,500 tokens → $0.000750
  User message (always uncached):                     500 tokens → $0.001500
  Output:                                           2,000 tokens → $0.030000

Daily cost per tenant (1 generation, 0 retries):
  = (2500/1M * 3.75) + (500/1M * 3.00) + (2000/1M * 15.00)
  = $0.009375 + $0.001500 + $0.030000
  = ~$0.041 per day per tenant

With 1 retry (cache read for system prompt):
  = $0.030750 + $0.001500 + $0.030000 = ~$0.062 per day
```

At Sofa Belle pilot scale (1 tenant), Phase 5 costs under $2/month. Even at 50 tenants: ~$75/month — well within the product's unit economics.

**Cost tracking:** Store `cost_usd` as `NUMERIC(10,6)` in `daily_insights` (D-16). Log all four token fields (`input_tokens`, `output_tokens`, `cache_read_input_tokens`, `cache_creation_input_tokens`) from `response.usage` so the true cache hit rate is visible in the DB.

```python
# InsightService._compute_cost() — exact formula from SPEC.md Section 10
cost_usd = Decimal(str(
    (usage.input_tokens / 1_000_000) * 3.0 +
    (usage.output_tokens / 1_000_000) * 15.0
))
# Note: this formula uses full input_tokens (not net of cache reads) for simplicity.
# Actual cost is lower when cache_read_input_tokens > 0 (cache reads cost $0.30/MTok, not $3.00/MTok).
# For budget tracking, the simple formula is conservative and sufficient for MVP1.
```

**Caching strategy:** The system prompt cache reduces per-call input cost by ~83% on the second and subsequent calls each day (retries, manual re-runs). The cache TTL is 5 minutes. Because Phase 5 runs once daily, the first call of each day always pays the write cost. Retries within the same invocation hit the cache. This is the expected and optimal behaviour — no additional caching layer (Redis, application-level) is needed for Phase 5.

**Sub-task routing:** Phase 5 has one model call: `claude-sonnet-4-5` for the full report. No routing to cheaper models (e.g., `claude-haiku-3-5`) is warranted — the Romanian business reasoning and salesperson-specific action generation require Sonnet quality. If future phases add classification steps (e.g., routing user chat questions to the right tool), use Haiku at $0.25/$1.25 per MTok for those routing decisions.

**Latency budget:** Target end-to-end time for `generate_daily_insights` Celery task is under 30 seconds (including DB reads, Claude API call, DB write). Claude Sonnet 4.5 typical TTFT is ~1s; full response for 2,000 output tokens is ~8-12s. The task runs at 06:00 and must complete before Sofa Belle opens at ~09:00 — no strict deadline constraint for MVP1. Set Celery `soft_time_limit=120` and `time_limit=180` as a safety net against hanging API calls.

**D2 — Number Cross-Check (AI-06)**
Priority: Critical

PASS: All numeric values extracted from `problems[].description` and `summary` narrative text match a value in the input `kpi_snapshot` or `detected_problems[].estimated_loss_ron` within ±2% tolerance. # tests/unit/services/insights/test_number_validator.py
```python
import re
from decimal import Decimal

# Regex that matches Romanian-formatted numbers (both . and , as separators):
# "23.400", "2.8%", "8,3", "351", "47.320,50"
NUMBER_PATTERN = re.compile(
    r'\b(\d{1,3}(?:[.,]\d{3})*(?:[.,]\d+)?|\d+(?:[.,]\d+)?)\s*%?'
)

def extract_numbers(text: str) -> list[float]:
    """Extract all numeric values from Romanian-formatted narrative text."""
    results = []
    for match in NUMBER_PATTERN.finditer(text):
        raw = match.group(1).replace(".", "").replace(",", ".")
        try:
            results.append(float(raw))
        except ValueError:
            pass
    return results

def within_tolerance(actual: float, expected: float, tolerance_pct: float = 2.0) -> bool:
    if expected == 0:
        return actual == 0
    return abs(actual - expected) / abs(expected) * 100 <= tolerance_pct

def test_number_cross_check_pass(insight_with_real_numbers, kpi_snapshot, problems_input):
    """AI-06: numbers in narrative must match input within ±2%."""
    numbers_in_text = extract_numbers(insight_with_real_numbers.summary)
    input_values = [
        float(kpi_snapshot["l_to_c_pct"]),
        float(kpi_snapshot["leads_total"]),
        *[float(p["estimated_loss_ron"]) for p in problems_input],
    ]
    for n in numbers_in_text:
        # Each number in text should match at least one input value within tolerance
        assert any(within_tolerance(n, v) for v in input_values), (
            f"Number {n} in narrative text has no matching input value within ±2%"
        )

def test_number_cross_check_rejects_fabricated_ron(
    insight_with_fabricated_ron, kpi_snapshot, problems_input
):
    """Revenue fabrication: invented RON amount must be caught."""
    numbers_in_text = extract_numbers(insight_with_fabricated_ron.summary)
    input_values = [float(p["estimated_loss_ron"]) for p in problems_input]
    fabricated = [
        n for n in numbers_in_text
        if n > 1000  # large RON amounts in text
        and not any(within_tolerance(n, v) for v in input_values)
    ]
    assert len(fabricated) > 0, "Test fixture should contain a fabricated RON amount"
    # The validator should have caught this and triggered a retry
```

## 6. Guardrails

### Online (Real-Time)

This is an internal batch pipeline, not a user-facing interactive system. Guardrails run synchronously within the Celery task before writing to the DB — not in an HTTP handler. There are no end-users waiting for a real-time response, so latency is not a constraint here. Two guardrails run on every generation attempt:

| Guardrail | Trigger | Intervention | Implementation |
|-----------|---------|--------------|---------------|
| **Pydantic schema validation** | `DailyInsightResponse.model_validate(tool_block.input)` raises `ValidationError` | Block: discard response, increment retry counter; after 3 failures write `status='fallback'` | Already in `InsightService.run()` try/except block (Section 4 code) — no new code needed |
| **Number cross-check** | `_numbers_match()` returns `False` — extracted narrative numbers deviate >2% from input KPI values | Block: discard response, increment retry counter; after 3 failures write `status='fallback'` | `number_validator.py` `cross_check()` function called in `InsightService.run()` retry loop |
| **PII payload check** | `build_user_message()` detects customer-identifiable fields in `context_json` before API call | Block: strip PII fields from `context_json` before sending; log `insight.pii_stripped=True` | Implemented in `prompt_builder.build_user_message()` — filter `context_json` to only `{rule_id, current_value, expected_value}` |

The schema validation and number cross-check guardrails are already wired into the retry loop (Section 4). The PII check is preventive — it runs before the API call, not after.

**What is not a guardrail here:** There are no content safety guardrails (hate speech, harmful content). This is a B2B business analytics report generated from pre-validated KPI data. The only safety concern is GDPR PII in the payload, which is addressed by the PII payload check above. No Anthropic Moderations API call is needed.

### Offline (Flywheel)

The flywheel runs weekly via product owner review + DB query. At Sofa Belle pilot scale (1 tenant, 1 report/day), "sampled batch" means reviewing 5 reports per week — small enough to do manually without additional tooling.

| Metric | Sampling Strategy | Action on Degradation | Query |
|--------|------------------|-----------------------|-------|
| **Retry rate** (number cross-check failures per day) | 100% — logged to `daily_insights.input_tokens` ratio and structlog `insight.number_mismatch` events | If retry rate > 20% over 7 days: review number_validator.py tolerance; consider adding few-shot examples to system prompt | `SELECT date, (input_tokens / 3000) AS estimated_retries FROM daily_insights WHERE date >= NOW() - INTERVAL '7 days'` (rough proxy: extra retries = extra input tokens) |
| **Fallback rate** (status='fallback' days) | 100% | If fallback rate > 0 in any 7-day window: inspect `raw_response` column on failed rows; check for Anthropic API changes or schema drift | `SELECT COUNT(*) FROM daily_insights WHERE status='fallback' AND date >= NOW() - INTERVAL '7 days'` |
| **Cost per generation** | 100% — stored in `cost_usd` column | Alert if daily cost exceeds $0.20 (5x expected) — indicates cache miss or runaway retry loop | `SELECT date, cost_usd FROM daily_insights ORDER BY date DESC LIMIT 14` |
| **Salesperson attribution quality** | 5 reports/week — product owner reviews `payload_json` for any `underperforming_salesperson` problems | If owner or sales manager reports name attribution error: add failed case to reference dataset, update system prompt roster if salesperson list changed | Manual review via Insights page (Phase 7) |
| **Romanian language quality drift** | 5 reports/week — product owner spot-checks | If diacritics errors appear (caught by `test_romanian_diacritics_present`) or owner reports "sounds wrong": run Promptfoo Romanian fluency judge against last 7 days of reports | `SELECT date, payload_json->>'summary' FROM daily_insights ORDER BY date DESC LIMIT 7` |
| **Weekly action plan quality** | 5 reports/week — owner checks if weekly_action_plan items were acted on | If owner repeatedly ignores weekly plan: investigate whether items are too generic; add more specific examples to system prompt | Owner feedback via FUTR-05 (future: thumbs up/down) |

## 7. Production Monitoring

**Tracing Tool:** `daily_insights` PostgreSQL table + structlog JSON logs + Sentry

Arize Phoenix (the gsd-eval-planner default) is not installed for Phase 5. This is a deliberate decision for the SMB pilot: the `daily_insights` table already captures every signal needed (status, token counts, cost, raw response, generated_at), structlog provides JSON event logs queryable via `docker compose logs`, and Sentry catches exceptions. Adding a tracing platform would be over-engineering for 1 tenant generating 1 report per day. Revisit when scaling to 10+ tenants or when the owner requests a quality dashboard.

**Key Metrics to Track (via `daily_insights` table queries):**

| Metric | Column / Log Event | Normal Range | How to Query |
|--------|-------------------|-------------|--------------|
| Daily generation status | `status` | `'success'` every day | `SELECT date, status FROM daily_insights ORDER BY date DESC LIMIT 30` |
| Retry rate (schema + number failures) | structlog `insight.number_mismatch`, `insight.pydantic_validation_failed` | 0 retries/day | `docker compose logs worker | grep insight.number_mismatch | wc -l` |
| Cost per generation | `cost_usd` | $0.030–$0.065/day | `SELECT AVG(cost_usd), MAX(cost_usd) FROM daily_insights WHERE date >= NOW() - INTERVAL '7 days'` |
| Token usage (cache effectiveness) | `input_tokens` | ~3,000 tokens/call (lower = cache hit) | `SELECT date, input_tokens, output_tokens FROM daily_insights ORDER BY date DESC LIMIT 14` |
| Generation latency | `generated_at - created_at` | < 30 seconds | `SELECT date, EXTRACT(EPOCH FROM (generated_at - created_at)) AS latency_sec FROM daily_insights ORDER BY date DESC` |

**Alert Thresholds:**

| Condition | Threshold | Alert Method | Urgency |
|-----------|-----------|-------------|---------|
| Generation failure | `status = 'fallback'` for any date | Sentry error (already captured by Celery autoretry exhaustion) + manual check of `raw_response` column | High — owner sees degraded report |
| Cost spike | `cost_usd > 0.20` on any single day | Manual daily check of `daily_insights` table | Medium — indicates retry loop or cache miss |
| Consecutive fallback days | `status = 'fallback'` for 2+ consecutive days | Sentry alert (configure via Celery task `on_failure` callback) | Critical — owner has received AI-failed report two days running |
| Missing generation | No `daily_insights` row for yesterday by 07:00 Bucharest | Celery beat monitoring — if task did not fire, Redis/Celery infrastructure issue | Critical — owner has no report for the day |
| Retry rate increase | > 3 `insight.number_mismatch` events per day for 3+ days | Review structlog for pattern; check if KPI data schema changed | Medium — may indicate prompt drift or new anomaly type |

**Sentry configuration for Phase 5:**

```python
@app.task(
    bind=True,
    autoretry_for=(Exception,),
    max_retries=3,
    soft_time_limit=120,
    time_limit=180,

    ...

def notify_insight_failure(self, exc, task_id, args, kwargs, einfo):
    """Sentry capture + structlog on Celery task failure (all retries exhausted)."""
    import sentry_sdk
    sentry_sdk.capture_exception(exc, extras={"task_id": task_id, "tenant_id": args[0]})
    log.error(
        "insight.task_failed",
        task_id=task_id,
        tenant_id=args[0],
        error=str(exc),
    )
```

**Smart Sampling Strategy:**

Phase 5 generates exactly one report per day. "Sampling" means selecting which reports to review manually each week. The selection weights toward:

1. **Always review** any day where `status != 'success'` — fallback reports need diagnosis.
2. **Always review** any day where `input_tokens > 9000` — this indicates a retry loop where the cache was missed or extra tokens were consumed, warranting investigation.
3. **Weekly review (5 reports):** product owner reviews the 5 most recent `status='success'` reports for: salesperson name correctness (compare against MEFI), Romanian language quality, and whether the weekly action plan items match what the owner's team actually did that week.
4. **Monthly calibration (first month of production):** Sofa Belle owner rates all 30 reports using the actionability rubric (1b "Actionability at 06:00 standup"). Use these ratings to calibrate the Promptfoo LLM judge — target ≥ 0.7 Spearman correlation. After calibration, reduce to weekly sampling.

```sql
-- Weekly review query: pull the 5 reports that need attention this week
SELECT
    date,
    status,
    input_tokens,
    cost_usd,
    generated_at,
    payload_json->>'summary' AS summary_preview
FROM daily_insights
WHERE tenant_id = '<sofa_belle_tenant_id>'
  AND date >= NOW() - INTERVAL '7 days'
ORDER BY
    CASE WHEN status != 'success' THEN 0 ELSE 1 END,  -- failures first
    CASE WHEN input_tokens > 9000 THEN 0 ELSE 1 END,   -- high-token days second
    date DESC
LIMIT 5;
```
